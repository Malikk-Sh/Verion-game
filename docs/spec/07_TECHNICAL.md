# Техническая спецификация — Three.js / mobile-first

**Актуальный игровой срез S2.6 (9.10.2026):** правила ручного размещения/подбора, двух мировых портов, трёхслотовой печи, переносимой воды, двухслотового кислородного генератора, заправки по нажатию, ящиков и мини-попапа квестбука описаны в [VERDANA_S26](../prototypes/VERDANA_S26.md). Они заменяют противоречащие ранние решения. Состояние v6; оплаченные запасы и работы мигрируют без сброса.

**Статус:** архитектура полной игры ещё не реализована целиком. **S1 «Основа»** ([описание](../prototypes/VERDANA_S1.md)) реализует §3 (часы: тики 50 мс, ≤5 шагов, без догонки) и §9 в объёме одного региона: IndexedDB `vireon` v1 со страницами по хешу, атомарным манифестом, 3 ревизиями, lease 5/15 с, экспортом/импортом `.vireon.json`; V17–V20 проходят автотестами на fake-indexeddb. **S1.1:** состояние v2 (contentVersion 1.1.0) — костюм из 4 частей, быстрый доступ = ячейки 1–6, смещение суточного цикла мира; чистая миграция сохранений и файлов экспорта 1.0.0 без потерь (инвентарь, износ, газ баллонов). Суточный цикл 600 с дня + 360 с ночи от общего activeTime; карта видимости солнца перепекается инкрементально при повороте света с плавным переходом. Хеш SHA-256 считается собственной реализацией без `crypto.subtle`, чтобы работать и в автономном файле. Выполнен [визуальный образец B4](../prototypes/VERDANA_B4.md) (после [B3](../prototypes/VERDANA_B3.md) и [B2](../prototypes/VERDANA_B2.md)): мир 560×560 м с чанками рельефа и LOD, запечённая карта видимости солнца плюс каскад теней вокруг игрока, рендер с процедурным небом, контроллер, объединение статических моделей, мобильный UI, профили качества, процедурный звук и Fullscreen API; ограничения и отличия описаны отдельно. Мобильная производительность не измерена. Версии зависимостей фиксируются lockfile при создании приложения; не использовать `latest` в воспроизводимой сборке. Технические API сверены по первичной документации, ссылки в §09.

## 1. Стек и границы

TypeScript, Three.js WebGLRenderer/WebGL2, Vite для сборки, DOM/CSS поверх canvas для интерфейса. Одиночная логика без сервера. Собственный кинематический контроллер и дискретная геометрия вместо обязательного тяжёлого физического движка. Web Worker для генерации/перестроения геометрии и, после профилирования, подготовки сохранений. Не требуются WebGPU, SharedArrayBuffer, cross-origin isolation, OffscreenCanvas или File System Access picker.

Целевые среды проверки: Safari/iOS 17+ и Chrome/Android 120+ с WebGL2 и IndexedDB; это выбранная нижняя граница тестирования, не декларация полной совместимости всех таких телефонов. При недоступном WebGL2 понятный экран требований, импорт/экспорт имеющихся сохранений остаётся доступным, если хранилище читается. При недоступном IndexedDB нельзя притворяться, что автосохранение работает: предложить повтор/экспорт текущего состояния и не начинать обычную сохраняемую сессию без информирования.

## 2. Модули и модель данных

| Simulation | Единственные игровые часы, команды, порядок систем | Не зависит от кадров renderer |

| Networks | Графы энергии/газа/жидкости/предметов | Не телепортирует между несвязанными компонентами |
| Habitats | Стеклянные помещения, шлюзы, распределители/климат (`src/game/rooms.ts`, без DOM и three.js) | Не использует физическую CFD |
| Ecology | Грядки, озеленение, планетарные счётчики | Не создаёт обычную еду из визуальных инстансов |
| Combat | Спавн, ИИ, урон, добыча | Не атакует базы отсутствующих миров |
| Persistence | Ревизии, миграции, экспорт/проверки | Не сохраняет GPU-объекты/функции |
| Renderer / Audio / UI | Представление снимков и отправка команд | Не являются вторым источником игровых ресурсов |

Основные DTO:

- `WorldMeta { id, seed, generatorVersion, contentVersion, activeTicks, planetId, revision }`.
- `ItemInstance { guid, itemId, count, durability?, fluids?, energy?, modules?, packedMachine? }`; no cyclic references.
- `Machine { guid, typeId, worldId, gridPos, ports, inputs, outputs, WIP, energyBuffer, enabled, recipeId, rngState, cycleCounter }`.
- `WIP { recipeId, reservedInputs, reservedOutputCapacity, progressMs, materializedOutputs?, reservedPlanetWork? }`.
- `Habitat { id, cellsHash, volume, oxygenMilliGU, tempMilliC, cleanliness, topologyRevision, sealed }`.
- `TerrainChunk { key, baseVersion, deltaEncoding, revision, dirty }`.
- `PlanetProgress { pressureWork, thermalWork, oxygenWork, cleanCycles, waterCommitted, bioPlots, freeWater }`.
- `Player { worldId, pose, hp, hunger, equip, inventory, hazardTimers, emergencyBreathMs, knownRecipes, beds }`.
- `Travel { id, origin, target, paidFuel, phase, cargoSnapshot, rocketGuid }`; phase prevents double spend after reload.

В definitions только стабильные ID. Локализованное имя не является ключом сохранения. Все объекты имеют GUID, поколения индексов массивов помогают не применять отложенное сообщение к новому объекту на старом месте.

## 3. Время и порядок симуляции

Физика персонажа/попаданий: фиксированные 50 мс (20 Hz), рендер интерполирует. Экономика всех миров: 1 с. Голод/кислород персонажа интегрируются по fixed-step, а не только раз в секунду. Планетарные показатели меняются по атомарно завершённым партиям, интерфейс сглаживает визуально.

Порядок секундного шага: команды/изменения топологии → состояние погоды/дня → доступные производители энергии → распределение → газ/жидкости/предметы → запуск/прогресс/завершение машин → грядки/комнаты → планетарные эффекты → маркировка dirty. Новые выходы, созданные на шаге, доступны следующему шагу: это исключает зависимость скорости линии от порядка обхода массивов. UI показывает «ожидание следующего цикла», когда оно заметно.

Рабочий прогресс `dt×min(1, allocatedPower/requestedPower)`, если есть остальные условия. Потраченная энергия точно равна allocatedPower×dt. Голод/время/топливо задаются миллиединицами; переполнение целых проверяется. Если у рецепта EU=0, он не получает бесплатный обход требований среды/катализатора/времени.

Покинутые миры выполняют **тот же секундный алгоритм**, без renderer/physics персонажа/боевого ИИ. При загрузке мира нет расчёта `Date.now−lastPlayed`. На hidden сразу stopClock, очистка накопителя кадров, лучшая попытка сохранения. После resume старый frame delta не используется. При тяжёлом кадре maximum 5 физических шагов; отставание больше 250 мс останавливает продвижение общего игрового времени до догрузки, а не ускоряет только экономику. Все системы используют одно принятое activeTime.

Не делать аналитический «часовой скачок» производства в 1.0: при активном мире и 512 машинах секундный расчёт проще проверять, чем аппроксимацию сложных сетей. Если бюджет не укладывается, оптимизировать структуры/спящие машины, а не разрешать отсутствующей базе игнорировать расход.

## 4. Производство, RNG и транзакции

Команда игрока имеет monotonically increasing commandId и ожидаемую revision объекта. Применение дважды не дублирует крафт/перенос. Изменение входов, выхода и WIP одной машины происходит одной логической транзакцией в Simulation. Между двумя инвентарями transfer проверяет source/destination revisions, лимит стака и вместимость, затем одновременно уменьшает/увеличивает; ни UI, ни animation event не создают предмет.

Просеивание использует независимый xoshiro128** поток машины (4×uint32), seed derived из seed мира + GUID машины при первом создании. Каждый исходный грунт — отдельный набор бросков по отсортированным itemId; набор доступных результатов фиксируется в момент начала партии, смена сетки во время партии запрещена. Упаковка/перенос/сохранение сохраняют RNG и cycleCounter. N порций сжатого грунта выполняют N таких же наборов. RNG результата обновляется и фиксируется одновременно с материализацией выхода; переполнение вывода не даёт переброс.

Новые жилы (S4, D33) не используют `Math.random`: задержка, точка и размер берутся из seed мира, номера следующей жилы и длины очереди, поэтому повтор того же сохранения даёт ту же жилу. Точки — проверенные данные `VEIN_SPOTS` (генератор `tools/gen_vein_spots.ts` запущен один раз, игра их не сэмплирует); в `stateVersion: 8` жила хранит ID точки, а не координаты, и импорт отклоняет неизвестную точку, чужой материал, две жилы в одной точке, остаток больше размера и превышение пределов.

Культурный bonus seed имеет свой поток грядки и делает ровно один бросок при созревании; выход фиксируется до нажатия «Собрать». Размещение/перенос зрелой грядки не повторяет бросок. Мир/погода/враги/лут/сита имеют разные потоки, чтобы лишний визуальный эффект не менял находку.

## 5. Сети

Порты привязаны к клетке/грани, типу, направлению, допустимому ресурсу и cap. Электричество/каждый газ/каждая жидкость/предметы имеют отдельные графы. Ребро содержит пропускную способность и состояние клапана. Компоненты пересчитываются только при изменении соединений, а не каждый кадр; dirty component пересобирается до следующего экономического шага.

Передача газа/энергии должна учитывать **узкое ребро**, не только общую сумму источников. Выбран ограниченный детерминированный поиск увеличивающих путей от источников к потребителям по приоритету. Остаточная пропускная способность уменьшается на поток, общий источник уменьшается один раз. Внутри приоритета — пропорциональные квоты целыми единицами (метод наибольших остатков) с переносом дробного остатка каждого потребителя на следующие дефицитные тики; тики без дефицита этот остаток не обнуляют. Остаток ограничен ±1 единицей, живёт в памяти и не сохраняется: после перезагрузки расхождение меньше единицы на потребителя (S3; заменяет прежний round-robin по persistent cursor). Все объёмы конечны; loop сетки не размножает поток. Логической «одной бесконечной ёмкости всей сети» нет.

Буфер на входе машины отделяет сетевую передачу от потребления рецепта. Один порт не смешивает ресурсы; пустой бак может сменить тип только по явному сбросу настройки, не автоматически в середине цикла. Предметные передатчики не используют глобальный поиск склада — только заданная пара.

## 6. Terrain, чанки и коллизии

Плавная поверхность: заранее генерируемый heightfield 32×32 м чанками с шагом высоты 2 м и треугольниками. В пределах dig volume участок heightfield вырезается, заменяется воксельной геометрией; закрытые внешние стыки имеют переходную полосу 1 м, не подлежащую раскопке за границей объёма. Коллизия и визуальная граница используют одну маску, чтобы не было скрытого пола после удаления блока.

Воксель 1 м, чанк 16³, материал uint16. Не по отдельному Mesh на блок. Генератор выдаёт только открытые грани и объединяет одинаковые соседние (greedy meshing); непрозрачное/прозрачное раздельно. Редактирование загрязняет сам чанк и соседей по затронутым граням. Worker получает chunk revision и border samples; результат принимается только при совпадении revision, устаревший mesh освобождается. Максимум 2 активные задачи перестроения, backlog ограничивает новые клики с видимым прогрессом, не теряет команду.

Игровая коллизия читает актуальную сетку блоков немедленно; capsule sweep против локальных AABB, поверхность вне зон — треугольники heightfield. Изменение в пределах тела запрещено. Mesh может догнать на следующем кадре; цель B0 <100 мс, при большем отставании редактирование приостанавливается до обновления. Падающие блоки выполняются очередью до 64 перемещений/физический шаг, каждый перенос атомарен, блок не превращается одновременно в предмет и грунт.

На астероиде декоративная сфера с маской участков, локальные зоны имеют свои grid transforms; каждый блок нормаль берёт из поверхности/грани, поддержка когтей вычисляется из контакта. Изменение глобального up применяется только контроллером когтей/станции; физика обычного свободного движения хранит выбранный вектор притяжения. Нельзя применять плоский Y-up jump к прикреплённой нижней поверхности.

**Решение S4 (рельеф, D28).** Высоты `rawHeight`/`heightAt` в игровой области −200…360 м не меняются: от них зависят сохранённые постройки (y по 9 точкам), проверка линий 12 м в 3D при загрузке, размещение травы и тесты. «Более приятный рельеф» достигается только видом: цвет склона по фиксированной сетке 2 м и кривизна по 1 и 4 м одинаково в обоих LOD (нет скачка цвета при смене блока), тёмные ложбины и светлые гребни, боковая проекция текстуры и слоистость на крутых склонах, макрошум против повтора, рябь песка поперёк ветра (только рыхлый песок, 9–22 м от камеры), а также более рельефные внешние горы за пределами проходимой области (чисто декоративные, сетка 10 м, 8 секторов). Изменение высот в игровой области возможно только с миграцией сохранений и отдельным решением Малика.

## 7. Герметичность и навигация

Помещения (S4, D31) выводятся из `base.glass` (отсортированные уникальные ключи клеток) и `base.doors` чистой функцией: flood fill по воздушным клеткам со связностью по граням; стекло, шлюз и грунт (правило четырёх углов) газ не пропускают. Область, вышедшая за габарит стекла и шлюзов +1 или без стекла/шлюза над своим столбцом, — снаружи (рельеф — карта высот, поэтому это тот же вердикт, что и по габариту, только раньше); 1025-я клетка — «слишком большой объём». Результат кэшируется по массивам базы и пересчитывается только при изменении стекла или шлюзов, не при движении игрока. Правка (`editRooms`) переносит газ целыми milli-GU: q·|R∩C|/|R| в каждую новую компоненту, остаток — к наибольшему пересечению; доля, вышедшая наружу, уходит сразу (D32), затем q ≤ 20×V; T и c взвешены по объёму, новый объём добавляет наружную T и чистоту 0. Нетронутое помещение сохраняет зону точно. `predictRemove` считает потерю без изменения состояния для подтверждения. Путь утечки ищется только при открытии окна. Рендер: объединённые грани по чанкам 16³ (перестраиваются только изменённые), коллизии стекла и шлюзов — в пространственном хэше 4 м, который контроллер опрашивает по прямоугольнику шага.

Перестроение триггерят изменение блоков, состояние дверей/вентилей и установка оборудования, а не движение игрока. Переход двери внутри уже известных зон может использовать кэш границ. Навигация врагов — грубая сетка 1 м в радиусе 48 м, колонка высоты/свободности, A* бюджет 128 раскрытий на запрос и очередь до 2 запросов/физический шаг. Удаление/добавление блока инвалидирует локальный tile. До нового пути враг останавливается/делает локальный обход, не идёт сквозь стену. На астероиде навигация по графу граней поверхности и входам пещер, без обещания полноценного динамического navmesh всего шара.

## 8. Рендер и производительность

Повторяющиеся машины/растения/блоки одинакового материала — InstancedMesh по пространственным группам, не один гигантский batch на весь мир. Изменённая матрица обновляет instance buffer; bounding volumes группы пересчитываются для корректного culling. Выгруженные геометрии/текстуры освобождаются через dispose, иначе переходы миров накапливают GPU-память.

Low: DPR≤1, дальность 80 м, один directional light без теней и ambient, до 2 декоративных point light возле игрока, вода без отражений, 512 частиц. Medium: DPR≤1,5, дальность 120 м, простая тень солнца 1024², до 4 point light. Как эти лимиты соблюдаются в текущей сборке (Medium называется «Стандарт») — подраздел «Рендер S4» ниже. Игровая освещённость для спавна отдельна и не зависит от отключённых теней/качества.

Цели B0: 30 FPS, p95 кадра ≤33,3 мс в контрольной сцене; рендер ≤150 draw calls / 250k видимых треугольников на Low. CPU: физика ≤3 мс/кадр, UI≤2, секундный production step ≤8 мс с распределением работы по кадрам до общего барьера. Память процесса измеряется где доступно; целевой живой JS heap <180 MiB, GPU-ресурсы <128 MiB. Это бюджеты для проверки, не гарантии всех телефонов.

| Лимит мира B0 | Значение / поведение |
| --- | --- |
| Машины | 256 на планету; 64 на станцию; 0 на астероиде |
| Строительные блоки | 8192 на планету/станцию, включая развёрнутые шаблоны |
| Собственные грунтовые блоки | 16384 на планету, 2048 на астероид; природные изменения отдельно |
| Активные грядки | 128 на мир, считаются устройствами |
| Светильники | 192 на мир; игровые клетки света кэшируются |
| Кабель/трубы/передатчики | 4096 рёбер на мир |
| Сущности | По лимиту мира §03; не копятся в отсутствующей сцене |
| Копаемые данные | 12 областей×64×64×32 на планету; генерировать по запросу, не разворачивать одновременно все массивы |

Достижение лимита отклоняет только новое размещение с числом использовано/максимум. Не удалять старое содержимое, не продавать лимит, не замораживать тайно 257-ю машину. Просеивателей можно построить десятки внутри общих бюджетов. Если профилирование провалено, исправить алгоритмы/графику и открыто пересмотреть бюджет B0 до релиза.

### Рендер S4: фактически соблюдаемые бюджеты

Числа B0, проверены в Chromium/SwiftShader и unit-тестах, не на телефоне.

| Что | Low | Standard | High |
| --- | --- | --- | --- |
| Point light (постоянный пул, создаётся при загрузке) | 2 | 4 | 4 |
| Частицы: пулы сколов/пыли/искр + пылинки ветра | 416 + 96 = 512, эмиссия ×0,5 | 1440 + 320 | 1440 + 640 |
| Следы ботинок (кольцевой буфер, 1 draw call) / время исчезновения | 48 / 30 с | 96 / 60 с | 160 / 90 с |
| Тень солнца | нет | 1024², ±42 м | 2048², ±60 м |
| Рельеф: сетка 1 м / средний уровень 2 м (дальше 4 м) | до 55 / 70 м | до 55 / 110 м | до 80 / 140 м |

- **Свет без перекомпиляции.** Печь, лампа стеклянного помещения (по одной на помещение), дверь и салон капсулы — скрытые источники; каждый кадр они одалживают положение, цвет и яркость ближайшим активным слотам пула (печь > помещение > дверь > салон при равном расстоянии). Число источников в сцене не меняется при установке, сборе или загрузке станций, поэтому освещённые шейдеры не перекомпилируются синхронно.
- **Тень солнца** следует собственному направлению света (обновляется после поворота на 0,25°) и собственному центру (сдвиг после 3 м пути, округление до текселя), а также перерисовывается явно при появлении станции и движении двери шлюза; при ходьбе это примерно одна перерисовка на 3 м вместо каждого кадра. `normalBias` ≈ один тексель (8,2 см Standard, 5,9 см High). Внешние 10% охвата тени плавно гасят её — без резкой границы на ±42/60 м и без дополнительных выборок. Запечённая видимость солнца перепекается после поворота света на 0,05 рад.
- **Частицы**: мёртвый спрайт получает размер 0, размер точки считается в пикселях кадрового буфера и ограничен 20% его высоты, в GPU выгружается только изменённый диапазон, рисуется только живой. Пылинки ветра — один instanced draw call без покадровой выгрузки. Сколы освещены уровнем дня/ночи и не светятся ночью.
- **Средний уровень рельефа.** Между мелкими блоками и радиусом качества стоит уровень 2 м (1120 треугольников на чанк 40 м вместо 3840). Его вершины лежат на той же сетке высот столкновений, нормали и цвет в общих точках совпадают с уровнем 1 м, блок меняет уровень только целиком (до готовности остаётся прежний), щели закрыты юбками. Высоты игры, тени и следы не зависят от выбранного уровня.
- **Прочее**: декоративная галька рисуется только в 70 м (список обновляется каждые 8 м, на Low скрыта); кнопки HUD в игре без `backdrop-filter` поверх canvas; внешние горы разбиты на 8 секторов (отсекаются за камерой) и не принимают карту тени, лежащую вне их охвата.
- **Карта (S4, D34).** Рельеф карты — растр 560×560 (1 м на пиксель), строится один раз кусками по 8 мс после подготовки сцены и при открытой карте; рисуется одним `drawImage` под преобразованием вида. Холст карты масштабируется по `devicePixelRatio` (не больше 2). Наложение перерисовывается при взаимодействии и примерно 4 раза в секунду; закрытая картой 3D-сцена в это время рисуется 4 раза в секунду (`sceneInterval` 250 мс). Время построения и кадра карты на телефоне не измерено.
- **Стоимость грунта.** Шейдер рельефа делает 5 выборок текстур вместо 2 (боковая проекция на крутых склонах, две выборки макрошума); время GPU на телефоне не измерено.
- **Добыча (S4, п. 7).** Не больше одного дополнительного draw call: одна оболочка трещин (прозрачная копия самой крупной сетки прицельной залежи с той же геометрией и диапазоном отрисовки; узор — ячейки Вороного по мировым координатам, UV у объединённых моделей нулевые). Куски осыпи исчезают диапазоном отрисовки объединённой сетки, без новых объектов; твёрдые куски и искры — те же пулы частиц и лимиты. Один луч `Raycaster` на удар (около двух в секунду). Анимация есть только у залежи под ударом или в обрушении и идёт по времени сцены (стоит на паузе); тень перерисовывается в начале и в конце обрушения. Пулы частиц, оболочка трещин и перчатка компилируются при загрузке (`compileAsync`), без компиляции на первом ударе.
- **Проверка.** `verify:performance` требует на Low ≤150 draw calls и ≤250k треугольников в контрольных видах, пул point light 2/4, ≤512 частиц вместе с пылинками, следы после ходьбы и их исчезновение за 30 с, пылинки во всех качествах и их отсутствие при снижении движения, не больше ⌈путь/3 м⌉+2 перерисовок тени при ходьбе и идентичные пиксели паузы с частицами, следами, пылинками и трещинами; на Low при добыче (с оболочкой трещин) тоже ≤150 draw calls, блок железа — ровно 9 ударов с отделением последним, точка удара — по лучу; при снижении движения взмах не больше 35% и без отклика модели. Кадровые частоты из SwiftShader не являются FPS телефона.

### Диагностика S2.7

Опциональная запись в настройках собирает ограниченные RAF/CPU-этапы, события ввода, longtask/LoAF при поддержке, сохранения и геометрию; экспорт JSON, без данных мира/рюкзака и без автоматической отправки. PMREM готовится при загрузке; живые обновления используют кэш. Shade/LOD выполняются по частям с целевым бюджетом 2 мс. Low использует DPR 0,75; меню ограничивают только частоту 3D, сохраняя fixed simulation и UI. Тесты и ограничения устройства: `../prototypes/VERDANA_S27.md`. Бюджеты B0 выше остаются целями, не обещанием FPS.

## 9. Сохранения и экспорт

Браузерное хранилище может быть очищено пользователем/системой и ограничено квотой. `navigator.storage.persist()` запрашивается после первой базы, отказ не блокирует игру и не обещает вечного хранения. `estimate()` используется для приблизительного предупреждения. Файл экспорта — независимая пользовательская копия; он не обновляется автоматически при следующем автосохранении [T2–T5].

IndexedDB `vireon`, schemaVersion=1. Stores: `worldSlots`, `revisionManifests`, `statePages`, `chunkPages`, `definitionsVersions`, `settingsBackup`. Стабильная страница данных имеет GUID и contentHash; манифест ревизии содержит ссылки на все используемые immutable pages. GPU-меши, кэш навигации и производные графы не сохраняются.

### Атомарная ревизия

1. На границе Simulation step получить согласованный снимок dirty state, player, RNG, WIP и всех затронутых миров. Поставить `snapshotTick`; последующие игровые изменения идут в новый dirty set, не меняют снимок.
2. Кодировать страницы вне активной IDB-транзакции. Сжатие terrain — RLE по материалам и sparse delta `(localIndex, materialId)`; выбрать меньший из двух вариантов. Каждая страница ≤256 KiB, проверка hash до записи.
3. Записать новые immutable pages короткими транзакциями. Пока манифест не переключён, эти страницы не являются активным миром. Сбой здесь оставляет старую ревизию рабочей.
4. Одной readwrite-транзакцией проверить ожидаемую baseRevision, записать complete manifest и обновить `worldSlots.activeRevision`. Запрос durability `strict` использовать там, где он поддерживается; не приравнивать `oncomplete` во всех браузерах к гарантии физической записи при внезапной потере питания [T4].
5. После подтверждения отметить снимок сохранённым. Хранить последнюю активную и две предыдущие полные логические ревизии, разделяя неизменённые страницы. GC удаляет только страницы, не достижимые ни из одного из этих манифестов и не используемые незавершённой записью текущей сессии.

Сохранение каждые 30 активных с, плюс смерть/возрождение, изучение чертежа, взлёт/посадка, смена мира, ручная команда. Частые запросы объединяются, критический переход ждёт подтверждения записи; при ошибке места переход не списывает ресурсы повторно и остаётся в восстановимом состоянии. На hidden — best effort снимок, но периодический commit главный механизм. Нельзя откладывать единственную запись до unload.

**Несколько вкладок:** один writable lease на worldSlot через IDB с token/heartbeat раз в 5 с, expiry 15 с. Перед каждым commit проверить token и baseRevision в той же транзакции. Новая вкладка предлагает «Мир открыт в другой вкладке»; принудительное открытие после явного выбора «Открыть здесь» отзывает прежний token, прежняя сессия останавливает изменение, сохраняя возможность экспорта своего локального снимка как отдельного файла. Отсутствие ответа BroadcastChannel не позволяет автоматически отзывать действующий lease: скрытая или замороженная вкладка может не отвечать. Без подтверждения разрешено занять только свободный или истёкший lease. Время lease — реальное, только для блокировки записи, не для игрового прогресса.

### Формат файла

`.vireon.json`, UTF-8, envelope:

`{ magic:'VIREON', formatVersion:1, contentVersion:'1.0.0', generatorVersion:1, exportedAt, manifest, pages:[...], sha256 }`.

`sha256` считается от канонически сериализованных manifest/pages без самого hash и метки времени; обеспечивает обнаружение порчи, не защиту от читов. Локальная одиночная игра не требует античита. Строки ограничены по длине; нет кода/URL для исполнения, прототипных свойств и пользовательских скриптов. Максимум файла 64 MiB несжатого JSON; при превышении бюджет нужно пересмотреть или разбивать по слотам, не обрезать данные. Сжатый транспорт можно добавить позже с лимитом распаковки, но 1.0 не зависит от ZIP/пикеров.

Экспорт: подготовить согласованный snapshot, Blob + download; на платформах с Share API возможно «Поделиться файлом», fallback обычная ссылка скачивания. Импорт: выбрать input[type=file], проверить размер до чтения, magic/version/hash, ID/типы/целочисленные диапазоны, ссылки, отсутствие рекурсивных контейнеров/дубликатов GUID и объёмы terrain. itemId должен быть собственным ключом реестра предметов, инструментов или баллонов соответствующего типа; унаследованные имена вроде `constructor` и `__proto__` не являются предметами. В S1 счётчик `world.nextDropId` должен быть строго больше числовых суффиксов всех существующих `drop-N`, иначе следующее выпадение повторит ID; такой импорт отклоняется до записи. Затем записать **новый** worldSlot через staging pages; существующий мир не перезаписывается. Неподдерживаемая будущая версия отклоняется с сохранением файла пользователя.

Миграция: чистая функция vN→vN+1 на копии, с проверкой до commit. Базовый generatorVersion старого мира сохраняется: смена генератора не перегенерирует уже изменённый грунт. Для удалённых itemId нужна явная таблица replacement/refund в миграции, а не пропуск неизвестного предмета. Должна сохраняться возможность экспортировать повреждённый слот для диагностики без автоматического «исправления» потерей инвентаря.

### Ошибки и восстановление

QuotaExceededError: остановить новые изменения, показать «Не удалось сохранить», предложить экспорт, очистку только ненужных старых миров по явному выбору и повтор. Не удалять последние рабочие копии молча. Повреждённая активная ревизия: проверить предыдущую и предложить восстановление с датой/потерянным интервалом. Пустой новый мир не подменяет старый автоматически. При недоступном crypto.subtle на небезопасном origin использовать только локальное сохранение и показать, что проверяемый экспорт требует HTTPS; production всегда HTTPS.

## 10. Контент и поставка

`catalog.json` загружается как definitions, валидируется в development/CI. Tech/world/effect/crop definitions должны быть перенесены из спецификации в отдельные JSON при реализации с теми же ID. Не смешивать компоненты представления с балансом. Контент expansion включается явным флагом; сохранение помнит доступный набор, отключение расширения с предметами не удаляет их — загрузка остаётся в том же наборе либо требует совместимой версии.

Первичная поставка статический HTTPS-сайт, без API-секретов. Service worker кэширует версионированные ассеты после успешной загрузки; офлайн-доступ к уже загруженному приложению возможен, но не начисляет офлайн-прогресс. Новая версия активируется из меню после сохранения/перезапуска, не подменяет код во время активной сессии. Пользовательские сохранения не должны попадать в Cache API вместо IndexedDB.

Локальные диагностические показатели: frame time, draw calls, счётчики машин/чанков, время шага/сохранения, размер страниц, число ошибок. Нет обязательной отправки аналитики/геолокации/учётной записи. Экспорт диагностического отчёта только по действию игрока, без содержимого личных файлов устройства.

## Состояние крафта и прогресса S2.5

Начиная с `stateVersion: 4`, каждый корпус сохраняет `level` (1; 2 допустим только для workbench). Формат запрещает очереди hand/верстака I и более пяти суммарных партий верстака II. Миграция состояния 3 сначала проверяет прежние поля, затем устанавливает уровень I и убирает недоступные ручные очереди. Неоплаченные будущие ручные рецепты удаляются; оплаченные машинные ресурсы остаются в input, WIP/output остаются без изменений. Миграция не выдаёт ключа, улучшения или питания. Отсутствующее level в v4/v5 считается повреждением. Электрический порт открывается только у верстака II; все длины/направления сетей остаются строго валидируемыми. Уровень, буферы, очередь и WIP проходят существующие атомарные IndexedDB-страницы и экспорт/импорт.

`stateVersion: 5` добавил `progress.quests`: ограниченные массивы `facts` и `completed`, а также выбранный игроком `tracked` (ID вехи или null). Допустимые факты и ID перечислены в `questFacts.ts` / `questCatalog.ts`; неизвестные значения, дубликаты и превышение границ отклоняются до записи. Миграция v4 добавила только пустую историю квестов и сохранила уровень II, очереди, WIP, топливо и газ без изменений. v1–v3 проходят прежние миграции, затем получают те же поля прогресса; v6 (ящики, упакованные корпуса, переносимая вода) и v7 (S3: отрастание травы, новые залежи, поворот корпусов, повтор крафта) мигрируют без потерь. Текущая версия — одна `stateVersion: 8` (S4) из двух частей: стеклянные помещения D31 (`base.glass`, `base.doors`, `base.zones`, проход через шлюз; см. следующий раздел) и новые жилы D33 (`world.veins`, очередь `world.respawn`, счётчик `world.nextVeinId`). `migrateRaw` после прежней цепочки выполняет два шага, каждый по наличию своих полей, а не только по номеру: сначала шаг помещений (`toGlassRooms`: v7 или версия ≥7 без `glass`/`doors`/`zones`), затем шаг жил (`toVeins`: v7 или версия ≥7 без любого из трёх полей жил; пустые жилы, уже выработанные нетравяные залежи встают в очередь). Так загружаются сохранение S3 (v7), файл превью v8 с помещениями, но без жил, и файл превью v8 с жилами, но с готовым куполом; строгая проверка идёт после обоих шагов. Шаги идемпотентны, полное сохранение v8 повторно не мигрирует, версия никогда не понижается. Старый клиент отклоняет неизвестную версию, а не отбрасывает новую базу.

## Стеклянные помещения S4: состояние v8

Часть v8 о помещениях (S4, D31) заменяет готовый купол помещениями из стекла. `world.base` получает `glass` (отсортированные уникальные ключи клеток, не больше 8192), `doors` (`{id, x, y, z, rot}`: нижняя клетка шлюза 1×2, id `door-N` из общего `nextId`, не больше 32), `zones` (`{cell, q, temperature, purity, lossRemainder}` — одна на помещение, `cell` — наименьший ключ его клеток, не больше 64) и `passage` (`{doorId, direction, remainingMs, paid}` или null). У построек больше нет `zone` и 80-элементного `shell` (≈600 байт на постройку). Валидация: ключи в границах области строительства (с запасом 5 клеток для сохранённых краевых куполов), шлюзы не пересекаются со стеклом и друг с другом, q ≤ 20×V; зона, чьего помещения после пересчёта нет, отбрасывается без ошибки, помещение без зоны начинается пустым. Пересечение стекла со станцией проверяется только при новом размещении.

Шаг помещений v7 → v8 (`toGlassRooms`) зависит от полей, а не только от номера: он выполняется для v7 и для любого сохранения версии ≥ 7 без `base.glass`/`doors`/`zones` (v8-файл превью, где купол остался); сохранение с этими полями больше не трогается, версия никогда не понижается. Каждый купол становится стеклянной оболочкой вокруг внутренности 4×4×3 (клетки x−2…x+1 × z−2…z+1, по три уровня воздуха над нижним негрунтовым уровнем столбца, верх общий) с четырьмя угловыми колоннами; зона сохраняет q (не больше 20×48), T, чистоту и остаток потерь. Шлюз встаёт в одну из двух средних клеток стены на уровне самого высокого из трёх столбцов (дверь, внутренняя и внешняя посадка): сначала прежняя передняя стена, затем остальные по повороту. Берётся первый вариант, чьи посадки свободны по правилам нового шлюза (стекло других оболочек, шлюзы, грунт, станции, скалы и залежи); если такого нет, остаётся прежняя передняя стена. Платформы купола больше нет: станции, стоявшие внутри старого купола, опускаются на рельеф (`stationY`, как при новом размещении), игрок внутри — тоже; остальные станции остаются на месте. Проход через купол завершается сразу: игрок ставится в точку посадки своего направления. Игрок, тело которого после миграции оказалось бы в стекле или шлюзе (оболочка на 1 м шире старых стен, обычно у старого шлюза), ставится в точку посадки ближайшего бывшего купола: внутреннюю, если грудь была внутри купола, иначе внешнюю. Упакованный купол в рюкзаке, ящиках, кучах и слотах станций становится предметом `dome` без `packed` (воздух в рюкзаке не переносится) и разбирается карманным рецептом `dismantle_dome` (64 стеклоблока + шлюз). Факты квестов `item:dome` и `craft:craft_dome` остаются допустимыми (`LEGACY_FACTS`). v1–v7 проходят прежние миграции, затем этот шаг и шаг жил. Новая жила не появляется в стеклоблоке, шлюзе и его площадках и внутри габарита помещения (`roomBlockers` в `veinBlockers`); карта рисует стеклянные постройки контуром, а шлюз — целью «Шлюз» с карточкой помещения (`glassPrints` в `mapFootprintSources`). Старый клиент отклоняет v8 и не перезаписывает базу.

`production.ts` регистрирует успешный результат крафта, положительно выделенное питание, завершённую работу верстака II без присутствия игрока, фактическую заправку и одновременную автосборку с пригодным стеклянным помещением. Отмена, полный выход, отсутствие питания и стартовый полный баллон не засчитывают эти действия. `quests.ts` наблюдает сохранившиеся материалы и постройки, выводит только необходимые предшествующие материалы и закрепляет достижения независимо от порядка подсказок. Стартовые инструмент, баллон и пульпа не доказывают их изготовление. Историю уже потраченных предметов старого мира восстановить невозможно; события автоматизации и заправки нужно выполнить снова, если их факт не сохранён. UI читает модель прогресса и меняет только выбранную цель HUD; никаких наград или блокировок производства не вводится. Обновление обычного снимка сохраняет `progress.quests` вместе с посещениями и выбранным ориентиром.
